CAN clássico vs CAN FD

Os dois formatos usam o mesmo conceito de identificador e payload em um barramento CAN, mas não oferecem a mesma capacidade. Esta página mostra exatamente onde o projeto separa os contratos, as estruturas e os sockets.

mesmo barramento · capacidades diferentes

Resumo em uma frase

CAN clássico é otimizado para mensagens curtas e previsíveis; CAN FD mantém a arbitragem compatível, mas permite payload maior e uma fase de dados mais rápida quando o hardware suporta essa operação.

CAN clássico

  • Payload de 0 a 8 bytes.
  • Estrutura Linux: can_frame.
  • MTU SocketCAN: CAN_MTU.
  • Contrato do projeto: ICanBus.
  • Implementação: SocketCanBus.

CAN FD

  • Payload de 0 a 64 bytes.
  • Estrutura Linux: canfd_frame.
  • MTU SocketCAN: CANFD_MTU.
  • Contrato do projeto: ICanFdBus.
  • Implementação: SocketCanFdBus.

O que permanece igual

Identificador CAN

Ambos podem usar ID padrão de 11 bits ou ID estendido de 29 bits. O formato do payload não determina o tamanho do ID.

SocketCAN

Os dois usam PF_CAN, SOCK_RAW, filtros, poll, read e write.

Aplicação

O fluxo continua sendo criar um frame, enviar, aguardar uma resposta e interpretar os bytes segundo um protocolo.

Separação importante: CAN FD não significa automaticamente ID estendido. Um frame CAN FD pode usar um ID padrão de 11 bits.

Como ler: o array sempre possui capacidade para 64 bytes, mas frame.len informa quantos estão válidos. Se len == 12, somente as posições 0–11 fazem parte da mensagem; as posições restantes não são transmitidas como payload útil.

IDs padrão e estendidos

O valor armazenado na API representa o número do ID. A implementação acrescenta CAN_EFF_FLAG somente quando o valor ultrapassa o limite padrão de 11 bits. Essa flag informa ao kernel que o frame usa o formato estendido. 

// ID padrão de 11 bits
frame.can_id = 0x123;

// ID estendido de 29 bits
frame.can_id = 0x1234567 | CAN_EFF_FLAG;

Não confunda: usar CANFD_MTU significa enviar a estrutura CAN FD completa. Isso não obriga o ID a ser estendido.

O que muda na API C++

Contrato clássico

class ICanBus
{
public:
    virtual CanBusStatus sendFrame(
        uint32_t id,
        const uint8_t* data,
        uint8_t length) = 0;
};

Contrato CAN FD

class ICanFdBus
{
public:
    virtual CanFdBusStatus sendFrame(
        uint32_t id,
        const uint8_t* data,
        uint8_t length,
        uint8_t flags = 0) = 0;
};

O contrato CAN FD possui flags porque o frame pode declarar recursos como bitrate switch. Ele também retorna CanFdBusReceiveResult, que contém CanFdFrame, em vez de CanBusReceiveResult. Essa duplicação mantém as duas interfaces independentes.

CANFD_MTU normalmente equivale a sizeof(struct canfd_frame). Ele informa o tamanho da estrutura completa transferida ao socket. O payload real é indicado por frame.len e pode ser menor que 64 bytes.

Flags e bitrate switch

O frame CAN FD pode carregar flags adicionais. A constante do projeto CAN_FD_BITRATE_SWITCH corresponde à solicitação de troca para um bitrate maior na fase de dados.

Sem BRS

A arbitragem e os dados usam o bitrate nominal configurado.

Com BRS

A arbitragem começa no bitrate nominal e os dados podem usar o dbitrate.

sender.sendFrame(
    id,
    payload,
    length,
    CAN_FD_BITRATE_SWITCH);
Limite do vcan: a interface virtual testa frames e payloads, mas não possui temporização física nem bitrate real. BRS deve ser validado em hardware CAN FD.

Para o detalhamento dos campos FDF, BRS e ESI, consulte Estrutura do frame CAN FD.

Configuração dos sockets

Socket clássico

O socket CAN RAW já trabalha naturalmente com can_frame.

socket(PF_CAN, SOCK_RAW, CAN_RAW);

Socket CAN FD

O suporte FD precisa ser habilitado explicitamente.

int enableCanFd = 1;
setsockopt(
    socketFd_,
    SOL_CAN_RAW,
    CAN_RAW_FD_FRAMES,
    &enableCanFd,
    sizeof(enableCanFd));

Depois da habilitação, o socket FD pode receber frames FD e frames clássicos. Por isso a recepção aceita CANFD_MTU e CAN_MTU. Se uma classe quisesse aceitar somente FD, poderia rejeitar qualquer retorno diferente de CANFD_MTU.

Quando usar cada um?

CAN clássico

Use quando os sinais cabem em 8 bytes, a compatibilidade com ECUs antigas é necessária ou a rede já está definida como CAN 2.0.

CAN FD

Use para payloads maiores, atualizações de firmware, telemetria mais rica e menor tempo de ocupação do barramento.

Decisão de projeto

Escolha o contrato correspondente: ICanBus para CAN clássico ou ICanFdBus para CAN FD.
