Arquitetura do projeto Virtual CAN

ICanBus e SocketCanBus

Como uma interface C++ separa o contrato de comunicação da tecnologia usada para transportar os frames CAN.

Abstração + polimorfismo

A ideia central

O código que precisa enviar ou receber mensagens CAN não deveria precisar saber se o transporte é um socket Linux, um simulador, um driver de hardware ou um mecanismo de testes. Essa decisão pertence à implementação concreta. No projeto, essa divisão é feita entre ICanBus e SocketCanBus.

ICanBus

Contrato independente de transporte
  • Declara sendFrame.
  • Declara receiveFrame.
  • Declara setFilter.
  • Define os tipos e status comuns.
→implementa

SocketCanBus

Transporte concreto para Linux
  • Abre um socket PF_CAN.
  • Localiza a interface com ioctl.
  • Usa read, write e poll.
  • Converte entre CanFrame e can_frame.

Por que separar?

Menos acoplamento

O restante do programa depende de operações CAN, não de headers Linux como <linux/can.h> ou de descritores de socket.

Troca de transporte

Uma nova implementação, como MockCanBus ou uma implementação para outro sistema, pode obedecer ao mesmo contrato.

Testes mais simples

O código cliente pode receber uma implementação falsa e testar seu comportamento sem criar uma interface vcan0.

Princípio usado: o código de alto nível depende de uma abstração; detalhes de infraestrutura dependem dessa abstração. É uma aplicação prática da inversão de dependência.

O contrato em C++

Em C++, uma classe com pelo menos uma função virtual pura é uma classe abstrata. Ela descreve o que uma implementação deve fazer, mas não fornece uma implementação obrigatória para cada operação. 

class ICanBus
{
public:
    virtual ~ICanBus() = default;

    virtual CanBusStatus sendFrame(uint32_t id, const uint8_t* data, uint8_t length) = 0;

    virtual CanBusReceiveResult receiveFrame(std::chrono::milliseconds timeout) = 0;
};

virtual

Permite que uma chamada feita através de uma referência ou ponteiro para ICanBus chegue à implementação real do objeto.

= 0

Declara uma função virtual pura. Como consequência, ICanBus não pode ser instanciada diretamente.

override

Em SocketCanBus, confirma ao compilador que o método está substituindo uma função virtual da interface.

Destrutor virtual

Garante a destruição correta quando um objeto concreto é liberado através de um ponteiro para a interface.

A implementação concreta

SocketCanBus herda publicamente de ICanBus. Isso significa que um objeto SocketCanBus pode ser usado em qualquer lugar que aceite uma referência ou ponteiro para ICanBus. 

class SocketCanBus : public ICanBus
{
public:
    explicit SocketCanBus(const std::string& interfaceName);

    CanBusStatus sendFrame(...) override;
    CanBusStatus setFilter(...) override;
    CanBusReceiveResult receiveFrame(...) override;

private:
    int socketFd_ = -1;
};

O membro socketFd_ é um detalhe exclusivo do transporte SocketCAN. A interface não precisa conhecer esse descritor, nem saber que a implementação chama bind ou ioctl.

Como o polimorfismo acontece

O tipo estático de uma variável pode ser ICanBus, enquanto o objeto concreto criado em tempo de execução é um SocketCanBus. A função virtual seleciona a implementação correta. 

void runCommunication(ICanBus& bus)
{
    const uint8_t payload[] = {0x11, 0x22, 0x33};

    auto status = bus.sendFrame(0x123, payload, 3);
    auto result = bus.receiveFrame(std::chrono::milliseconds(1000));

    if (status == CanBusStatus::SUCCESS &&
        result.status == CanBusStatus::SUCCESS)
    {
        // O código usa o contrato, não o SocketCAN.
        auto id = result.frame->can_id;
    }
}

SocketCanBus linuxBus("vcan0");
runCommunication(linuxBus);

runCommunication não recebe SocketCanBus&; recebe ICanBus&. Portanto, uma implementação diferente pode ser passada sem modificar essa função.

Fluxo de uma transmissão

1

Cliente chama a interface

O cliente executa bus.sendFrame(id, data, length) usando apenas o contrato ICanBus.

2

Despacho virtual

Como o objeto real é SocketCanBus, C++ chama SocketCanBus::sendFrame.

3

Validação

A implementação verifica ID padrão, tamanho máximo de 8 bytes e ponteiro de dados.

4

Conversão de formato

Os dados do contrato são copiados para uma estrutura Linux can_frame.

5

Operação do sistema

write(socketFd_, &frame, sizeof(frame)) entrega o frame ao SocketCAN.

6

Status uniforme

A implementação traduz o resultado para CanBusStatus::SUCCESS ou TRANSMISSION_ERROR.

Fluxo de recepção

Antes da leitura

poll aguarda até que o socket tenha dados ou até o timeout. Retorno zero vira TIMEOUT; erro do sistema vira WAIT_ERROR.

Depois da leitura

read preenche um can_frame. Se o tamanho estiver incorreto, o status vira READ_ERROR.

Fronteira de tipos

O frame Linux é convertido para CanFrame, que usa std::array e não expõe headers específicos do kernel.

Resultado composto

CanBusReceiveResult transporta o status e um std::optional<CanFrame>. Em erro, o frame fica vazio.

Tipos e responsabilidades

ElementoResponsabilidadeConhece Linux?
ICanBusDefine operações que qualquer transporte CAN deve oferecer.Não
CanFrameRepresenta os dados comuns de um frame CAN clássico.Não
CanBusStatusPadroniza sucesso, timeout e falhas.Não
SocketCanBusImplementa o contrato usando SocketCAN.Sim
can_frameFormato definido pelos headers do kernel Linux.Sim

Como criar outro transporte

Uma implementação alternativa herda de ICanBus e implementa os três métodos. Ela pode usar memória, uma fila, um driver diferente ou um simulador. O código cliente continua igual. 

class MockCanBus : public ICanBus
{
public:
    CanBusStatus sendFrame(uint32_t id, const uint8_t* data, uint8_t length) override;

    CanBusStatus setFilter(uint32_t id, uint32_t mask) override;

    CanBusReceiveResult receiveFrame(std::chrono::milliseconds timeout) override;
};
Regra prática: o consumidor deve depender de ICanBus; somente a composição da aplicação deve decidir se cria SocketCanBus, MockCanBus ou outro transporte.

O que essa separação não faz

  • Não transforma automaticamente todos os transports em compatíveis: cada um ainda precisa implementar o contrato.
  • Não remove a necessidade de tratar CanBusStatus; a interface apenas padroniza os resultados.
  • Não permite instanciar ICanBus, porque ela é uma classe abstrata.
  • Não impede que uma implementação concreta tenha detalhes próprios, como um descritor de arquivo.
