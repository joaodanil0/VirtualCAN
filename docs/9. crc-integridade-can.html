CRC no CAN

O CRC é uma verificação matemática que ajuda o receptor a detectar alterações acidentais nos bits de um frame durante a transmissão. Esta página explica como o CAN clássico calcula e confere essa sequência, e o que acontece quando os resultados não coincidem.

CRC-15 · detecção de erro · CAN clássico

Para que serve o CRC?

Ruído elétrico, falhas de conexão ou outros problemas podem alterar bits enquanto um frame percorre o barramento. O transmissor calcula um valor de verificação a partir dos campos lógicos do frame e envia esse valor junto com a mensagem. Cada receptor faz o mesmo cálculo a partir do que recebeu e compara os resultados.

Resultados iguais

O valor recebido coincide com o calculado localmente. A verificação CRC passou; o frame ainda precisa passar pelas outras verificações do protocolo.

Resultados diferentes

O receptor detecta uma inconsistência de integridade e considera o frame inválido. O CRC detecta erros; não reconstrói nem corrige os dados corrompidos.

Verificação probabilística, não garantia absoluta: um CRC detecta muitas classes de erros de transmissão, mas não é autenticação e não torna impossível que uma corrupção específica passe despercebida.

O campo CRC no CAN clássico

No CAN clássico, o campo CRC é composto por uma sequência CRC de 15 bits seguida de um delimitador CRC recessivo de 1 bit. A sequência é calculada sobre os bits lógicos relevantes do frame, desde o SOF até o fim do campo de dados (ou do campo anterior ao payload, quando não há dados). O próprio CRC e os campos posteriores, como ACK e EOF, não entram nesse cálculo.

O CAN clássico usa o CRC-15/CAN, com polinômio gerador 0x4599, equivalente a x^15 + x^14 + x^10 + x^8 + x^7 + x^4 + x^3 + 1. O hardware CAN normalmente realiza esse cálculo; o código da aplicação fornece o ID e os dados e não precisa montar esses 15 bits manualmente.

O que o receptor faz

1

Recebe os bits do frame. O controlador CAN observa os campos transmitidos e remove bits de stuffing conforme a regra do protocolo.

2

Calcula o CRC esperado. A partir dos campos lógicos protegidos que recebeu, o controlador executa o cálculo CRC-15/CAN.

3

Compara os valores. Compara o CRC esperado com a sequência de 15 bits recebida no campo CRC.

4

Aceita ou sinaliza erro. Se coincidem, o frame pode continuar pelas verificações restantes. Se diferem, o receptor sinaliza erro conforme o estado de erro do nó; o frame não é aceito como válido.

Exemplo: um bit dos dados é alterado

Considere um Data Frame clássico com ID 0x123, DLC 3 e payload 11 22 33. O transmissor calcula a sequência CRC correspondente aos campos do frame e a envia. Se um bit do payload for alterado no caminho, o receptor calcula o CRC usando os bits recebidos e obtém outro resultado.

Transmissor: payload recebido como enviado = 11 22 33  → CRC enviado = C
Barramento:  um bit de dado se altera
Receptor:    payload observado             = 11 20 33  → CRC calculado = C'
Comparação:  C' ≠ C                         → erro de CRC

C e C' representam valores CRC simbólicos. Os valores exatos dependem de todos os bits protegidos do frame; não podem ser deduzidos apenas de um byte isolado.

Consequência: o receptor não entrega esse frame como uma mensagem válida. A sinalização de erro informa os nós no barramento de que a transmissão falhou; em condições normais, o transmissor tenta novamente conforme as regras de retransmissão e confinamento de erros do CAN.

Um frame válido precisa passar por verificações como CRC e stuffing antes de ser confirmado. O ACK é um bit separado no frame, não faz parte do valor CRC.

Limites e observabilidade

Não é criptografia

O CRC detecta corrupção acidental, mas não impede que um agente altere uma mensagem e recalcule um CRC válido. Autenticidade e proteção contra falsificação exigem mecanismos de segurança definidos pela aplicação.

O log não exibe a sequência

candump mostra frames já decodificados, normalmente sem os 15 bits de CRC. O controlador CAN e a pilha SocketCAN cuidam da validação antes de entregar o frame à aplicação.

Uma interface vcan permite testar o envio e a recepção de frames pela pilha de software Linux, mas não expõe a forma de onda física nem permite observar a sequência CRC transmitida sobre um par CAN real. CAN FD também usa campos e regras de CRC diferentes, incluindo sequências maiores; os detalhes desta página são para CAN clássico.

Para a estrutura completa dos campos, consulte Frames CAN: Data, RTR e ACK. Esta página trata do CRC-15 e da detecção de erros de integridade no CAN clássico.
