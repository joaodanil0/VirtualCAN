Frames CAN: Data, RTR e ACK

Um frame CAN transporta um identificador, campos de controle e, em um Data Frame, bytes de dados. Acompanhe a estrutura dos campos e veja como interpretar exemplos de dados, solicitação remota e confirmação.

CAN clássico · estrutura de frame · exemplos

Estrutura de um Data Frame padrão

Este é o formato clássico com identificador padrão de 11 bits. Os campos são enviados nesta ordem; o diagrama é conceitual e não está em escala.

SOF1 bit
ID11 bits
RTR1 bit
IDE + r02 bits
DLC4 bits
Dados0 a 8 bytes
CRC15 + delim.
ACKslot + delim.
EOF7 bits

Depois do EOF, há ainda um intervalo de intermission de 3 bits recessivos antes de um novo frame. O intervalo não é um campo do frame.

CampoTamanho / valorFunção
SOF (Start Of Frame)1 bit dominante (0)Significa “início do frame” (ou “início do quadro”); inicia a transmissão e sincroniza os nós.
Identificador11 bits no formato padrão; 29 bits no estendidoIdentifica o tipo/prioridade da mensagem. O ID não é necessariamente o endereço da ECU de origem ou destino.
RTR (Remote Transmission Request)Dominante (0) em Data Frame; recessivo (1) em Remote FrameSignifica “solicitação de transmissão remota”. Distingue frame com dados de solicitação remota no CAN clássico; o campo está na arbitragem.
IDE (Identifier Extension) + r0 (reserved bit 0)IDE identifica padrão/estendido; bits reservados são transmitidos nos valores definidos pelo protocoloIDE significa “extensão do identificador”. No formato padrão clássico, IDE=0 e r0=0; r0 é o bit reservado de posição 0. O formato estendido possui estrutura de arbitragem própria e bits reservados adicionais.
DLC (Data Length Code)4 bitsSignifica “código do comprimento dos dados” e indica o comprimento: 0 a 8 bytes no CAN clássico. Em Remote Frame informa o comprimento solicitado, embora o frame não transporte payload.
Dados0 a 8 bytesPayload do Data Frame. A interpretação de bytes e sinais depende do protocolo da aplicação.
CRC (Cyclic Redundancy Check)Sequência de 15 bits + delimitador recessivoSignifica “verificação cíclica de redundância” e permite detectar erros de transmissão. O delimitador separa o campo de CRC do campo ACK. Veja o guia detalhado de CRC.
ACK (Acknowledge)Slot de 1 bit + delimitador recessivoSignifica “confirmação”. Um receptor que validou o frame sinaliza o slot com nível dominante; o transmissor envia recessivo nesse instante.
EOF (End Of Frame)7 bits recessivosSignifica “fim do frame” e marca o encerramento do quadro.
Bits de stuffing: no CAN clássico, o transmissor insere um bit complementar após cinco bits consecutivos iguais desde SOF até a sequência CRC. Os bits inseridos não são campos adicionais do payload; o receptor os remove durante a decodificação. Por isso, a quantidade de bits efetivamente observada no fio pode variar. Veja o guia detalhado de bit stuffing.

O que muda no identificador estendido?

O formato estendido ainda é um frame CAN clássico, mas usa 29 bits de identificador e mais campos na arbitragem. Ele não é simplesmente um formato padrão com zeros acrescentados.

ID base11 bits
SRR1 bit
IDE1 bit
ID estendido18 bits
RTR1 bit
Controle, dados, CRC, ACK e EOFseguem no frame

O ID completo tem 11 + 18 = 29 bits. SRR (Substitute Remote Request) ocupa, no formato estendido, a posição em que estaria o RTR do formato padrão e é sempre recessivo (1). Assim, quando um frame padrão e um estendido começam com os mesmos 11 bits de ID, o padrão vence a arbitragem: o RTR dominante de um Data Frame padrão vence o SRR recessivo; se for Remote Frame, o bit IDE padrão dominante vence o IDE recessivo do estendido. O SRR ajuda, portanto, a preservar a prioridade do formato padrão. IDE (Identifier Extension) indica o formato estendido; os campos seguintes continuam com controle, payload e verificação.

Data Frame: transmissão de dados

Exemplo analisado

Considere um frame padrão com ID 0x123 e três bytes 11 22 33:

can0  123  [3]  11 22 33

Interface can0; ID 0x123; DLC=3; payload 0x11, 0x22, 0x33. A saída de candump mostra o ID em hexadecimal e os bytes separadamente.

Campos interpretados

SOF: 0. ID: 0x123 = 291 = 00100100011 em 11 bits. RTR: 0, pois é um Data Frame. IDE: 0, formato padrão. DLC: 3 (0011).

Payload: 3 bytes, enviados byte a byte, mais significativo primeiro dentro de cada byte. CRC depende dos bits do frame e é calculado pelo protocolo; o ACK depende da resposta dos receptores na rede.

Exemplo do projeto: mensagem de motor

O exemplo arduino_rtr.cpp transmite texto ASCII no ID 0x12. A string EV-ENGNR ocupa 8 bytes:

can0  012  [8]  45 56 2D 45 4E 47 4E 52

Os bytes hexadecimais correspondem aos caracteres ASCII E, V, -, E, N, G, N, R. O CAN só transporta esses bytes; é a aplicação que decide interpretá-los como texto.

Remote Frame (RTR): solicitação sem payload

Como funciona

Um Remote Frame CAN clássico pede os dados associados a um identificador. Ele contém o ID e um DLC que indica o comprimento esperado, mas não contém campo de dados. Seu bit RTR é recessivo (1).

Um nó que fornece aquela mensagem pode responder com um Data Frame usando o mesmo ID e os bytes pedidos. Essa resposta não é automática: depende de um nó e de uma aplicação configurados para atender à solicitação.

Exemplo analisado

Uma solicitação do ID 0x012 para três bytes pode aparecer assim, conforme a ferramenta:

cansend can0 012#R3
can0    012   [3]  remote request

R3 indica Remote Frame com DLC 3. O número 3 é o tamanho solicitado, não a quantidade de bytes que acompanham o frame RTR. Uma resposta possível seria um frame de dados com ID 0x012, DLC 3 e três bytes definidos pela aplicação.

Limite importante: Remote Frames pertencem ao CAN clássico. CAN FD não suporta Remote Frames; para solicitar dados numa aplicação CAN FD, use uma mensagem de solicitação definida pelo protocolo da aplicação.

No exemplo arduino_rtr.cpp deste repositório, o simulador envia o Data Frame EV-ENGNR e também um RTR com DLC 3 no ID 0x12. Ele demonstra a emissão e observação dos dois tipos de frame; não implementa, por si só, um nó que responde ao pedido remoto.

ACK: confirmação de recepção no barramento

O slot de ACK

O transmissor envia recessivo (1) durante o slot de ACK. Um ou mais nós que receberam o frame sem detectar erro dirigem o barramento para dominante (0) nesse slot. O delimitador de ACK seguinte é recessivo.

O que ACK não significa

ACK não confirma que a ECU destinatária lógica existe, que aceitou o ID, que interpretou os dados ou que executou uma ação. Confirma apenas que pelo menos um nó participante sinalizou recepção válida no nível do protocolo.

O transmissor observa no slotInterpretaçãoO que fazer com essa informação
Dominante (0)Ao menos um receptor sinalizou ACK.O frame foi confirmado no barramento; a aplicação ainda pode precisar de confirmação funcional própria.
Recessivo (1)Nenhum receptor sinalizou ACK.O transmissor detecta erro de ACK e, normalmente, tenta retransmitir de acordo com o protocolo.
Por que candump não mostra “ACK=0” no texto do frame? O ACK é um bit do nível físico observado durante a transmissão. Ferramentas de captura normalmente exibem o frame decodificado (ID, flags, DLC e dados), não a forma de onda nem o bit do slot ACK. A ausência de um campo ACK na linha impressa não quer dizer que o frame não foi confirmado.
