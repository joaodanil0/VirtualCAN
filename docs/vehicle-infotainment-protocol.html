Virtual CAN · protocolo de telemetria

Do sensor ao infotainment

Uma leitura detalhada da comunicação entre uma ECU do veículo e o infotainment: quem envia, quem recebe, como o frame é filtrado, como os bytes representam velocidade e temperatura e como o código C++ participa de cada etapa.

CAN clássico · request / response

O cenário

O veículo possui valores internos de velocidade e temperatura. O infotainment não acessa esses valores diretamente. Ele envia uma requisição pela rede CAN; a ECU recebe o comando, consulta seu estado atual, monta uma resposta e transmite os valores de volta.

Infotainment

Solicita os dados e decodifica a resposta para apresentar na tela.

Cliente CAN
↔ vcan0 · frames CAN

ECU do veículo

Reconhece o comando, prepara a telemetria e devolve a resposta.

EcuSimulator
Importante: o infotainment não conversa diretamente com uma variável C++ da ECU. Mesmo no simulador, os dados atravessam o mesmo formato de mensagens CAN que seria usado por módulos separados.

Contrato do protocolo

O protocolo deste exemplo possui uma requisição curta e uma resposta de quatro bytes. Os IDs são IDs CAN padrão de 11 bits; o primeiro byte da requisição é o opcode que identifica a operação desejada.

ECU → Infotainment0x6504 bytes69 03 DF 0087.3 km/h e 22.3 °C

Frame de requisição

O infotainment envia um frame com ID 0x600. O payload tem apenas um byte: 0x01. Esse byte é chamado de opcode e indica a operação READ_TELEMETRY.

constexpr uint32_t TELEMETRY_REQUEST_ID = 0x600;
constexpr uint8_t READ_TELEMETRY_COMMAND = 0x01;

const uint8_t request[] = {READ_TELEMETRY_COMMAND};
infotainmentBus.sendFrame(
    TELEMETRY_REQUEST_ID,
    request,
    sizeof(request));

Frame de resposta

A ECU responde com o ID 0x650 e quatro bytes. Cada valor é armazenado como um inteiro sem sinal de 16 bits, em little-endian, com escala de 10. Dividir por 10 transforma a unidade transmitida na unidade exibida.

Velocidade

0x0369 = 873 decimal. Como a escala é 10, o infotainment exibe 87.3 km/h.

Temperatura

0x00DF = 223 decimal. Como a escala é 10, o infotainment exibe 22.3 °C.

CanFrame telemetryResponse{};
telemetryResponse.can_id = 0x650;
telemetryResponse.len = 4;

// 873 = 87.3 km/h; 223 = 22.3 °C.
writeLittleEndian(telemetryResponse.data.data(), 873);
writeLittleEndian(telemetryResponse.data.data() + 2, 223);

Little-endian, passo a passo

Um inteiro de 16 bits ocupa dois bytes. Em little-endian, o byte da parte baixa vem primeiro e o byte da parte alta vem depois. Para codificar 873, que é 0x0369, o frame recebe o byte da parte baixa 0x69 e depois o byte da parte alta 0x03. 

void writeLittleEndian(uint8_t* destination, uint16_t value)
{
    destination[0] = static_cast<uint8_t>(value & 0xFF);
    destination[1] = static_cast<uint8_t>((value >> 8) & 0xFF);
}

uint16_t readLittleEndian(const uint8_t* source)
{
    return static_cast<uint16_t>(source[0]) |
           static_cast<uint16_t>(source[1] << 8);
}
Contrato dos dois lados: o transmissor e o receptor precisam concordar sobre ordem dos bytes, escala, unidade e sinal. Se a ECU enviar décimos e o infotainment interpretar inteiros, a tela exibirá um valor dez vezes maior.

O processo completo

1
Infotainment

Cria o frame de requisição com ID 0x600 e opcode 0x01.

2
SocketCanBus

Valida o ID e o tamanho, copia os dados para can_frame e chama write.

3
Kernel / vcan0

Entrega o frame aos sockets CAN ligados à interface virtual.

4
EcuSimulator

Chama receiveFrame; poll aguarda o frame e read o copia.

5
ECU

Compara can_id com 0x600 e data[0] com 0x01.

6
EcuSimulator

Para um comando válido, envia o frame configurado com ID 0x650.

7
Infotainment

Recebe apenas o ID 0x650, graças ao filtro configurado no socket.

8
Aplicação

Decodifica os pares de bytes, divide por 10 e apresenta velocidade e temperatura.

Como o filtro evita confusão

O socket do infotainment é configurado para receber o ID da resposta: 

infotainmentBus.setFilter(
    TELEMETRY_RESPONSE_ID,
    CAN_STANDARD_ID_MASK);

CAN_STANDARD_ID_MASK vale 0x7FF, portanto todos os 11 bits do ID padrão são considerados. O resultado é um filtro exato: 0x650 passa; 0x600 não passa nesse socket. A ECU, por outro lado, recebe a requisição porque seu socket não possui filtro restritivo nesse exemplo.

O papel de cada classe

ICanBus

Define o contrato de envio, recepção e filtros. Não conhece Linux nem o formato can_frame.

SocketCanBus

Converte o contrato para chamadas SocketCAN e traduz resultados do sistema para CanBusStatus.

EcuSimulator

Implementa a regra de negócio: reconhecer um comando e transmitir uma resposta. Depende de ICanBus.

ICanBus& ecuTransport = ecuBus;
EcuSimulator ecu(
    ecuTransport,
    0x600,
    0x01,
    telemetryResponse);

Essa referência é importante: a ECU não recebe um SocketCanBus&, mas um ICanBus&. Por isso, o mesmo simulador pode operar com uma implementação em memória durante um teste ou com SocketCAN em uma execução real.

Executando o exemplo

Com a interface virtual configurada e o projeto compilado:

sudo modprobe vcan
sudo ip link add dev vcan0 type vcan
sudo ip link set vcan0 up

cmake --build build
./build/vehicle_infotainment

A saída esperada é:

Velocidade: 87.3 km/h
Temperatura: 22.3 C
