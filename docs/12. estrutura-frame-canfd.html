Estrutura do frame CAN FD

Um frame CAN FD mantém os campos básicos de identificação e confirmação do CAN, mas acrescenta indicadores de formato, velocidade e estado do transmissor. Veja como FDF, BRS e ESI definem o frame e a sua transmissão.

O diagrama mostra a ordem conceitual dos campos de um frame de dados CAN FD com ID padrão de 11 bits. Campos de comprimento variável e regras de stuffing podem alterar o número de bits no fio.

Para o formato estendido, a arbitragem contém também SRR, IDE e os 18 bits adicionais do ID. A ordem detalhada dos campos de arbitragem varia conforme o formato de ID; o restante do frame FD mantém o mesmo propósito.

O bloco CRC está resumido no diagrama: o CAN FD inclui informações de contagem/paridade de stuffing e bits fixos próprios desse formato.

Campos que identificam e controlam o frame FD

CampoValor / posiçãoFunção
SOF1 bit dominante (0)Marca o início do frame e permite sincronização dos nós.
ID e IDEID padrão de 11 bits ou estendido de 29 bits; IDE diferencia o formatoIdentifica a mensagem e participa da arbitragem. CAN FD suporta os dois comprimentos de ID.

ESIDominante (0): transmissor Error Active; recessivo (1): Error PassiveError State Indicator informa o estado de erro do nó transmissor ao enviar o frame; não sinaliza o resultado do CRC deste frame.

Dados0 a 64 bytesPayload definido pelo protocolo da aplicação.
CRCCRC-17 (até 16 bytes) ou CRC-21 (20–64 bytes), informações de stuff count/paridade e delimitadorVerifica a integridade do frame; o comprimento de CRC depende do tamanho do payload e a codificação FD possui regras próprias de stuffing.

FDF, BRS e ESI têm funções diferentes: FDF escolhe o formato CAN FD; BRS escolhe se há troca de bitrate na fase de dados; ESI anuncia o estado de erro do transmissor.

BRS e as fases de bitrate

A arbitragem ocorre no bitrate nominal. Se BRS for recessivo (1), o transmissor e os receptores com configuração compatível mudam para o bitrate de dados depois do ponto de amostragem do bit BRS. A mudança de volta para o nominal ocorre no delimitador CRC.

Bitrate nominalSOF · arbitragem · FDF · res · bit BRS
Bitrate de dadosapós amostrar BRS
Bitrate de dadosESI · DLC · payload · CRC
Retornono delimitador CRC
Bitrate nominalACK · EOF

O desenho separa as fases, não é uma escala de tempo. Com BRS=0, não ocorre troca e o frame inteiro permanece no bitrate nominal; o frame continua sendo CAN FD.

Configuração é necessária: o valor de BRS não informa qual é o bitrate mais alto. A taxa de dados deve ser configurada de forma compatível em todos os nós e suportada pela rede física.

Para diferenciar a taxa nominal da taxa de dados e ver um exemplo de configuração, consulte Taxa nominal e taxa de dados no CAN FD.

DLC e comprimentos possíveis

O campo DLC continua tendo 4 bits, mas no CAN FD os valores acima de 8 mapeiam para comprimentos definidos, em vez de representar diretamente 9 a 15 bytes:

Os comprimentos CAN FD válidos são 0–8, 12, 16, 20, 24, 32, 48 e 64 bytes. Um DLC 9 significa 12 bytes, não 9. Consulte o guia detalhado do mapeamento DLC.

Exemplo de leitura de um frame FD

Considere um frame FD padrão com ID 0x123, BRS habilitado e DLC 9:

Formato: FD padrão       FDF = 1
ID:      0x123 (11 bits)  IDE = 0
RRS:     0 (dominante)    Remote Frame: não suportado
BRS:     1 (recessivo)    troca para bitrate de dados
ESI:     0 (dominante)    transmissor Error Active
DLC:     9                payload = 12 bytes
Dados:   10 20 30 40 50 60 70 80 90 A0 B0 C0
CRC:     CRC-17

Os campos e os dados são um exemplo didático. O controlador calcula e transmite os bits de CRC e de stuffing automaticamente; a aplicação fornece ID, flags e payload.

O que o FDF informa?

Que o formato do frame é CAN FD. O frame usa 12 bytes neste exemplo porque o DLC é 9, não porque FDF habilite BRS.

O que o ESI informa?

Que o transmissor estava Error Active quando enviou o frame. O estado do receptor pode ser diferente.

Compatibilidade e observação

Não é um Remote Frame

CAN FD não suporta Remote Frames. Para solicitar dados, uma aplicação FD define uma mensagem de requisição própria, com ID e payload segundo o protocolo do sistema.

Todos os nós precisam ser compatíveis

Um nó CAN clássico não interpreta um frame FD como um frame de dados clássico válido. Confirme que os nós ativos na rede suportam CAN FD antes de transmitir frames FD.

Ferramentas como candump mostram o frame já decodificado (ID, flags, DLC e payload), não uma captura dos campos no nível de bits. Uma interface vcan ajuda a testar aplicações SocketCAN, mas não simula a temporização física nem valida a troca de bitrate BRS em hardware.

Para comparar limites e a implementação SocketCAN do projeto, consulte CAN clássico vs CAN FD.
